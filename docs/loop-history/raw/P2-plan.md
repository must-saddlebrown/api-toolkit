Aturan presedensi `evaluate`. Dievaluasi berurutan; langkah pertama yang berlaku menentukan verdict:
1. Before tidak ada (stop sebelum before selesai) → `not_run [stop]` (`[not_started]` bila tanpa stop, pertahanan), `incomplete`.
2. Before tidak berupa counter valid (`complete`, nol action): transport → `error [verifier_failed, transport_error]`; tidak cocok `verify_match` → `error [verifier_failed]`; counter hilang/tidak valid → `error [counter_invalid]`; counter ≠ 0 → `inconclusive [initial_counter_not_zero]`.
3. After tidak ada (stop saat action, settle, atau after) → `not_run [stop]` (`[not_started]` tanpa stop), `incomplete`. Status action TIDAK dipakai sebagai bukti duplikasi (§6: status tidak cukup).
4. Hitung extras dari action dan skew.
5. After tidak valid → `error`: `[verifier_failed, transport_error]` / `[verifier_failed]` / `[counter_invalid]`, lalu extras (tanpa duplikat `transport_error`).
6. `delta = after - before` (before pasti 0). `delta > 1` → `fail [duplicate_side_effect]` + extras.
7. Jumlah action tercatat ≠ `concurrency` → `inconclusive`, reasons = extras (dimulai `dispatch_incomplete` bila tidak ada yang ambigu).
8. Ada action ambigu → `inconclusive`, reasons = extras.
9. `delta == 0` → `fail [action_not_executed]` + extras (hanya `dispatch_skew_exceeded` yang mungkin tersisa).
10. Skew > budget → `inconclusive [dispatch_skew_exceeded]`.
11. `delta == 1` → `pass [single_side_effect]`.

Completion `incomplete` hanya di langkah 1 dan 3. Semua jalur lain `complete`.

## Technical choices

| Topik | Keputusan | Alasan |
| --- | --- | --- |
| Struktur modul | Semua di `src/checks/race.rs`: `read_verifier` (murni), `action_allowed` (murni), `skew_ms` (murni), `evaluate` (murni), `run_with` (async, closure pengirim), `run` (membungkus `http::send`), `console_line`. `Stop`, `current_stop`, `wait_stop` dipindah dari `brute_force.rs` ke `checks/mod.rs` (`pub(crate)`) agar dipakai bersama. | Pola P1; matrix teruji tanpa jaringan; satu file per check (§13). |
| Signature | `pub async fn run(transport: &Transport, cfg: &config::Race, action: &ResolvedRequest, verify: &ResolvedRequest, stop: watch::Receiver<Option<Stop>>) -> CheckResult`. Prasyarat: config lolos `validate`. | Memakai tipe yang ada (`RaceRequests`). |
| Test double | `run_with<F, Fut>(send_one: F, cfg, stop)` dengan `F: Fn(Kind) -> Fut`, `Kind { VerifyBefore, Action, VerifyAfter }`. `Fn` (bukan `FnMut`) karena N future meminjam closure bersamaan; skrip test memakai `AtomicU32`/`Mutex` untuk state. | Closure, bukan trait (CLAUDE.md). |
| Klasifikasi verifier | `enum VerifyRead { Transport(TransportErrorCode), Mismatch, CounterInvalid, Counter(u64) }`. Urutan: `Err` → Transport; `!verify_match.matches(status, body)` → Mismatch; `body.and_then(\|b\| b.pointer(ptr)).and_then(Value::as_u64)` `None` → CounterInvalid; selain itu Counter. Body dibuang setelah itu. | Counter = integer ≥ 0 (counter side effect tidak bisa negatif); `as_u64` menolak float, string, bool, null, negatif. Before ≠ 0 dan after ≥ 0 membuat delta tidak pernah negatif. |
| Klasifikasi action | `allowed = Ok(r) && expected_action_statuses.contains(r.status)`. Body action tidak dibaca matcher, langsung dibuang. Transport error pada action = ambigu (INCONCLUSIVE `action_outcome_ambiguous` + `transport_error`), bukan ERROR. | §6 menaruh "action outcome ambiguous" di INCONCLUSIVE: action yang timeout mungkin sudah atau belum dieksekusi. Kata "network" di ERROR §6 dibaca sebagai jaringan verifier. Keduanya bukan PASS. |
| 202 | `validate` menolak 202 di `race.expected_action_statuses` (`ConfigError::Invalid`, rule "202 accepted/pending cannot prove a completed side effect (PLAN §6)"). Respons 202 saat run = status tidak diizinkan = ambigu. | Tanpa aturan ini pengguna bisa mengizinkan 202 dan mendapat delta1 PASS saat job masih pending; §6 melarangnya. Status pending lain (body) tidak bisa dideteksi: keterbatasan, dicatat. |
| Barrier dan release | Future action Rust bersifat lazy: buat N future dulu (tidak ada yang terkirim), lalu jalankan semuanya dengan `futures_util::future::join_all` dalam satu task; langkah pertama tiap future mencatat `Instant::now()` sebagai waktu dispatch. Ini barrier implisit: tidak ada byte keluar sebelum semua N siap. Tanpa `tokio::sync::Barrier` dan tanpa `spawn`. Sebelum release, cek `current_stop` sekali. `ponytail:` satu task berarti dispatch berurutan dalam satu poll (skew mikrodetik); pindah ke `JoinSet` + `Barrier` bila skew nyata terbukti terlalu besar. | Paling sedikit kode; `spawn` butuh `'static` sehingga request harus di-`Arc`, padahal `Secret` sengaja tanpa `Clone`. |
| Dependency | `futures-util = { version = "0.3", default-features = false, features = ["alloc"] }` (sudah di `Cargo.lock` 0.3.34 lewat reqwest/hyper, tanpa crate baru di tree). Bila `join_all` tidak tersedia dengan feature itu, pakai default features dan catat. Alternatif lebih malas tanpa dependency: loop `poll_fn` manual (±20 baris, memperkenalkan `Pin`/`Poll`); ditolak karena lebih sulit dibaca pengguna yang sedang belajar. | Sama dengan preseden `percent-encoding` (DECISIONS P0 S4). |
| Stop saat action | Tiap future action membungkus `send` dengan `select! { biased; wait_stop(rx.clone()) => None, r = send => Some(r) }`. `join_all` selalu selesai; action `None` = di-drop, dihitung di `actions_dispatched`, tidak dicatat di `actions`. Settle `sleep` dan verifier before/after juga di-`select!` dengan stop (pola P1). | Hasil parsial tersimpan (§8) tanpa kehilangan action yang sudah selesai. |
| Skew | Dihitung dari waktu dispatch SEMUA action yang terkirim (termasuk yang di-drop): `skew = max - min`, dibulatkan KE ATAS ke ms (`as_micros().div_ceil(1000)`), `None` bila nol action. Verdict membandingkan nilai ms yang sama dengan `max_dispatch_skew_ms` (`>` = berlebih). | Pembulatan ke atas mencegah 100,4 ms tampil sebagai 100 lalu PASS. Angka di report = angka yang dinilai. |
| Determinisme skew | Aturan skew diuji dengan array offset dispatch yang diketahui (`skew_ms` + `evaluate`). `run_with` dengan clock pause selalu skew 0; test hanya memastikan nilai ini mengalir ke evidence dan `evaluate`. Integrasi memakai `max_dispatch_skew_ms=1000`. | CLAUDE.md: verdict timing memakai data terkontrol, bukan performa laptop. Skew tidak bisa dipaksa di fixture karena diukur di sisi client. |
| Settle | `sleep(settle_ms)` setelah `join_all` selesai, lalu tepat satu verifier after. Tidak ada tunggu sebelum action. | §6 langkah 4; konsisten dengan fixed waits P0 (`settle_ms`). |

Urutan `actions` = urutan nomor. `counter_before` diisi bila before valid (termasuk ≠ 0). | Menuntaskan ponytail P1; JSON brute_force identik; `Eq` tetap bisa di-derive (tanpa f64). Distribusi status (§10) terbaca dari `actions[].status`. |
| Console | `race PASS delta=1 before=0 after=1 actions=5/5 skew=0/100ms reasons=single_side_effect`; `none` untuk nilai null; `actions` = action tercatat / `concurrency`. | §10 contoh `race PASS delta=1`, ditambah threshold dan reason seperti baris brute_force. |
| Fixture broken (sinkronisasi eksplisit) | `POST /broken/actions/{id}/apply-racy`: auth seperti healthy. Di bawah lock: baca count.
